SELF-HOSTED APPLICATION

Gym Tracker

A self-hosted Progressive Web App for tracking workouts, built around a containerized application and a separate infrastructure and observability layer.

Live Application View on GitHub
01 — Overview

More than just a workout tracker

Gym Tracker started as a personal application for recording workouts, but evolved into a practical environment for working with Linux, Docker, networking, CI/CD, monitoring and secure self-hosted infrastructure.

The application is built as a full-stack system with a Go backend, Vanilla JavaScript frontend and MariaDB. The application stack is separated from the monitoring and infrastructure stack, allowing both parts to be deployed and maintained independently.

The system is hosted on my own Linux server and exposed through a Cloudflare Tunnel, while administrative access and CI/CD deployment traffic use a private Tailscale network.

03 — What I built

From application to infrastructure

Containerized Application

The frontend and backend are built as separate Docker images and deployed through Docker Compose together with the MariaDB database.

Separate Infrastructure Stack

Monitoring and logging run independently from the application using a dedicated Compose stack.

Automated CI/CD

GitHub Actions builds versioned backend and frontend images, publishes them to GHCR and deploys them automatically to the server.

Secure Deployment

Deployment traffic travels through Tailscale and the server is accessed through SSH without exposing SSH directly to the public Internet.

Observability

Prometheus, Grafana, Grafana Alloy and Loki provide metrics, dashboards and centralized container logs.

Code Quality

SonarQube is integrated into the project to analyse code quality alongside the development workflow.

05 — Infrastructure

Application and infrastructure are deployed separately

Application changes

A normal push to main builds and deploys the backend and frontend automatically.

Automated workflow

GitHub Actions builds the images, pushes them to GHCR and deploys the selected version through Tailscale and SSH.

Monitoring changes

Changes to monitoring configuration should not rebuild or restart the application.

Separate infrastructure workflow

Monitoring configuration is deployed independently using a manual infrastructure workflow and its own Docker Compose project.

Full stack maintenance

Sometimes the complete application and monitoring environment needs to be stopped.

Controlled teardown

A separate manual workflow stops both Compose stacks while preserving persistent data.

06 — Problems & Solutions

Infrastructure problems became part of the project

The project evolved through solving practical problems rather than simply assembling a technology stack.

Problem

The server is located in a home network and does not provide a simple public inbound path to the application.

Solution

Cloudflare Tunnel provides external access to the application without directly exposing the home server to incoming Internet traffic.

Result: public application without traditional port forwarding.

Problem

CI/CD runners need administrative access to the server, but exposing SSH publicly would increase the attack surface.

Solution

GitHub Actions connects to the server through Tailscale and performs deployment over SSH inside the private network.

Result: no public SSH endpoint required.

Problem

Application containers and monitoring services have different lifecycle requirements.

Solution

The project uses separate Docker Compose projects for the application and infrastructure layers.

Result: monitoring can be updated independently.

Problem

Repeated deployments leave unused Docker images on a server with limited storage.

Solution

The deployment workflow performs Docker image cleanup after updating the application.

Result: unnecessary image accumulation is reduced.

Problem

A successful deployment does not necessarily mean that the application started correctly.

Solution

A dedicated post-deployment health check repeatedly requests the backend health endpoint and expects HTTP 200 before the workflow is considered successful.

Result: failed application startup is detected automatically.

10 — Lessons Learned

What this project taught me

Infrastructure is part of the application. A working backend and frontend are only one part of running a usable system.
Separating application and infrastructure lifecycles makes deployments easier to control and maintain.
CI/CD should not only deploy software — it should also verify that the deployment actually works.
Secure networking can remove the need to expose administrative services such as SSH publicly.
Monitoring becomes much more useful when metrics, logs and application health checks are considered together.
Self-hosting introduces real operational constraints: storage, networking, availability and maintenance become part of the engineering problem.

A workout tracker built as an infrastructure project

Gym Tracker combines application development with Linux, containers, CI/CD, secure networking and observability. The result is a system that I can actually run, monitor, break, fix and improve on my own infrastructure.
