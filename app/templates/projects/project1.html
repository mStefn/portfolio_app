Portfolio Infrastructure

A personal infrastructure project that evolved from an AWS-hosted application into a self-hosted Linux environment with automated CI/CD, containerized deployment and automated health checks.

01 / Overview

The portfolio is also an infrastructure project

This portfolio was built not only as a personal website, but also as a practical environment for learning Linux administration, Docker, AWS, networking, automation and CI/CD. The infrastructure has changed over time as new problems appeared and as the requirements of the project changed. It originally ran on AWS and was later migrated to my own Linux server after the AWS Free Tier ended. Instead of treating the migration as a rebuild from scratch, I used it as an opportunity to simplify the deployment process and keep the parts of the infrastructure that were actually useful.

02 / Evolution

From AWS to self-hosted Linux

The biggest change in the project was not a new technology, but a change in infrastructure strategy. The application remained containerized, while the environment around it evolved to match the actual needs of a personal project.

04 / Implementation

What I built

The project combines application deployment with infrastructure management. The goal was to reduce repetitive manual work and make deployments predictable.

Containerized deployment

The application is packaged as a Docker image and deployed through Docker Compose. This keeps the application environment reproducible between different hosts.

Automated CI/CD

Changes pushed to the main branch automatically trigger the build, image publishing and deployment process.

Infrastructure automation

AWS-specific tasks such as DNS updates, server lifecycle management and SSH access were automated instead of being handled manually.

Deployment verification

The current pipeline performs a health check after deployment and sends a Discord notification with the result of the workflow.

05 / Troubleshooting

Problems I had to solve

Most of the useful infrastructure work came from problems that appeared after the initial deployment. Instead of solving them manually each time, I automated the recurring parts.

Problem — dynamic EC2 public IP

The AWS instance received a different public IP address when it was started again. A static DNS record would therefore point to the wrong address after a restart.

Solution — automatic DNS update

The workflow retrieved the current EC2 public IP and automatically updated the Route 53 record during the startup process.

Result: the deployment did not require manual DNS changes after restarting the instance.

Problem — changing GitHub Actions runner IP

GitHub-hosted runners use changing public IP addresses, so permanently allowing one address for SSH access was not practical.

Solution — temporary SSH access

The AWS workflow detected the current runner IP, temporarily added it to the EC2 Security Group for SSH access, performed the deployment and removed the rule afterwards.

Result: CI/CD could connect to the server without leaving the runner's previous address permanently authorized.

Problem — Docker storage usage

Repeated image builds caused old Docker images to accumulate on the server. With limited disk space, this eventually became a deployment problem.

Solution — automatic cleanup

Unused Docker images were periodically removed using an automated cleanup process so that disk space did not have to be managed manually.

Result: fewer deployment failures caused by exhausted Docker storage.

Problem — unnecessary AWS runtime

A personal portfolio did not need an EC2 instance running continuously, especially while staying within the constraints of the AWS Free Tier.

Solution — scheduled EC2 lifecycle

The AWS workflow automatically started the instance on weekday mornings and allowed it to be stopped outside the required time window.

Result: the infrastructure used fewer AWS compute hours while the portfolio remained available during the intended period.

Problem — AWS Free Tier ended

Once the AWS Free Tier was no longer available, continuing to run a small personal portfolio on paid EC2 infrastructure was difficult to justify.

Solution — migration to self-hosted Linux

The application was migrated to my own Linux server. Docker and the existing deployment model made it possible to move the application without changing its core packaging.

Result: the portfolio continued running without the recurring EC2 infrastructure cost.

09 / Lessons learned

What this project taught me

Infrastructure problems are often easier to solve by automating the repeated task instead of fixing the symptom manually every time.
A small project can still require real infrastructure decisions around networking, security, storage and deployment reliability.
Cost is part of infrastructure design. The technically possible solution is not always the most sensible solution for a personal system.
Containerization made the migration from AWS to a self-hosted Linux server significantly simpler.
CI/CD is not only about building software. The deployment process also needs access control, verification and failure handling.
Troubleshooting and maintaining an existing environment taught me more about infrastructure than simply setting up the first working deployment.

A real infrastructure project, not just a website

The portfolio started as an AWS deployment experiment and evolved into a self-hosted Linux environment. Along the way, it became a practical project for learning deployment automation, troubleshooting, networking, containers and infrastructure maintenance.
