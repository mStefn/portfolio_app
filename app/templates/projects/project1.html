Portfolio Infrastructure

From an AWS-hosted application to a self-hosted Linux environment with automated CI/CD, monitoring and containerized deployment.

Overview

This project started as a simple portfolio application hosted on AWS. Over time, it became a practical infrastructure project where I could learn how to deploy, automate and maintain a publicly accessible application.

Instead of treating the portfolio as only a web application, I used it to experiment with infrastructure, CI/CD, networking, security and troubleshooting.

The infrastructure changed significantly over time. It originally relied on AWS EC2 and Route 53, while the current version runs on my own Linux server using Docker, Docker Compose and GitHub Actions.

Infrastructure Evolution

Initial AWS Infrastructure

The portfolio was initially hosted on an AWS EC2 instance running Linux and Docker. GitHub Actions was used to build and publish the application image to GitHub Container Registry and deploy it to the server.

Route 53 was used for DNS management and the EC2 instance was started and stopped automatically to avoid keeping it running continuously.

Current Self-Hosted Infrastructure

When the AWS Free Tier ended, keeping the portfolio on EC2 no longer made sense for a small personal project. I migrated the application to my own Linux server.

The application is now deployed using Docker Compose, while GitHub Actions handles the build, image publishing and deployment process.

Problems & Solutions

Dynamic EC2 Public IP

The EC2 instance received a different public IP address after being restarted. Instead of manually updating DNS, the deployment workflow retrieved the current IP and updated the Route 53 record automatically.

GitHub Actions Runner IP

GitHub-hosted runners use changing public IP addresses, which made permanent SSH access impractical.

During deployment, the workflow retrieved the runner's current public IP and temporarily added it to the EC2 security group for SSH access. After deployment, the rule was removed again.

Docker Disk Usage

Old Docker images gradually consumed the limited disk space on the server and eventually caused deployment problems.

I added a cleanup script that removed unused Docker images and scheduled it with cron.

AWS Cost

Running a personal portfolio continuously on EC2 was not necessary. To stay within the AWS Free Tier, the instance was automatically started and stopped using GitHub Actions.

This reduced unnecessary resource usage while keeping the application available when required.

Free Tier Expiration

Once the AWS Free Tier ended, continuing to pay for the EC2 infrastructure was difficult to justify for a personal portfolio.

Instead of removing the project or accepting the additional cost, I migrated it to my own Linux server while keeping the deployment process containerized and automated.

Current Architecture

The current environment is intentionally simple. The goal was not to build a large platform, but to create infrastructure that is easy to maintain and understand.

The application itself runs as Docker services managed with Docker Compose. The server is not directly exposed for administrative access; deployment is performed through a private Tailscale connection and SSH.

The current deployment process is triggered when changes are pushed to the main branch. It can also be started manually when required.

During deployment, GitHub Actions connects to the server through Tailscale, pulls the latest container image and recreates the application using Docker Compose.

After deployment, the workflow performs an external health check against the public application. The result is then reported through Discord.

Security & Maintenance

Security was kept relatively simple, but several practical measures were introduced as the project evolved.

  • Administrative access is performed through SSH.
  • Server access is handled through a private Tailscale network.
  • Application services run inside Docker containers.
  • Deployment is performed automatically through GitHub Actions.
  • Unused Docker images are removed after deployment.
  • Application availability is verified after deployment.

What I Learned

The most valuable part of this project was not setting up Docker or creating a GitHub Actions workflow. It was dealing with problems that appeared after the initial setup.

Working with changing IP addresses, SSH access, limited disk space, deployment failures and AWS costs showed me that infrastructure is not only about getting a system running. It is also about making it maintainable and understanding what happens when something changes.

The migration from AWS to my own server was also an important exercise in making infrastructure decisions based on actual requirements rather than simply using cloud services because they are available.

Looking back, I would separate the CI and CD responsibilities more clearly, build and publish images only when application code changes, and introduce better image retention and caching. These changes would make the pipeline more efficient without adding unnecessary complexity.
