Portfolio Infrastructure

A self-hosted portfolio infrastructure evolved from an AWS-based deployment into a Linux server environment with automated CI/CD.

Project Overview

This project started as a simple portfolio application hosted on AWS. Over time, I used it as a practical environment for learning Linux administration, Docker, CI/CD, networking, security and infrastructure automation.

Instead of treating deployment as a one-time setup, I gradually automated the parts that became repetitive or caused problems. This resulted in a small but realistic infrastructure project where changes to the application could be built, deployed and verified automatically.

The infrastructure also evolved because of real constraints. The initial AWS solution was useful for learning cloud deployment, but after the AWS Free Tier ended, maintaining a paid EC2 instance for a personal portfolio no longer made much sense.

Problems & Solutions

The most valuable part of the project came from problems that appeared after the initial deployment was working.

01

Dynamic EC2 Public IP

Problem

The EC2 instance received a new public IP address after being restarted. A static DNS configuration would therefore become invalid after each restart.

Solution

The deployment workflow retrieved the current EC2 public IP and automatically updated the Route 53 DNS record before deployment.

Result

DNS updates became part of the deployment process instead of requiring manual intervention.

02

GitHub Actions Runner IP

Problem

GitHub-hosted runners use changing public IP addresses. Permanently allowing SSH access from GitHub's infrastructure was therefore not a practical solution.

Solution

The workflow retrieved the current runner IP and temporarily added it to the EC2 security group for SSH access.

After deployment, the temporary rule was removed.

Result

Automated deployments could use SSH without leaving a permanent rule for changing runner addresses.

03

Docker Disk Usage

Problem

Repeated deployments caused unused Docker images to accumulate. The limited disk space on the server eventually became a deployment problem.

Solution

I introduced a Docker cleanup script which removed unused images and scheduled it using cron.

Result

Disk usage became predictable and deployments no longer depended on manually cleaning old images.

04

AWS Cost & Resource Usage

Problem

A personal portfolio did not require a continuously running EC2 instance. Keeping it online 24/7 would consume resources unnecessarily.

Solution

GitHub Actions was used to start the EC2 instance when required and stop it after the scheduled period.

Result

The infrastructure remained available when needed while reducing unnecessary AWS resource usage.

05

AWS Free Tier Expiration

Problem

Once the AWS Free Tier ended, paying for an EC2 instance solely to host a personal portfolio was difficult to justify.

Solution

I migrated the application to my own Linux server while keeping the deployment containerized and automated.

Result

The portfolio continued running without the recurring AWS infrastructure cost.

During deployment, the server pulls the latest container image and recreates the application using Docker Compose. Unused Docker images are removed afterwards to keep disk usage under control.

A separate health-check stage verifies the publicly accessible application after deployment. If the deployment or health check fails, the workflow reports the failure through Discord.

Security & Maintenance

Private Administration

Server administration is performed through Tailscale instead of exposing SSH directly to the public internet.

Containerization

Application components are isolated into Docker services and managed using Docker Compose.

Automated Deployment

Deployments are performed through a repeatable GitHub Actions workflow instead of manual server changes.

Post-Deployment Verification

The public endpoint is checked after deployment to verify that the application is actually available.

What I Learned

The most valuable part of this project was not getting the first deployment working. It was dealing with the problems that appeared afterwards.

Changing IP addresses, temporary SSH access, limited disk space, deployment failures and AWS cost constraints forced me to think about the infrastructure as something that needs to be maintained, not just configured once.

The migration from AWS to my own server was also an important infrastructure decision. Instead of using cloud services simply because they were available, I compared the actual requirements of the project with the cost and complexity of the infrastructure.

Looking back, I would separate the CI and CD responsibilities more clearly. I would also build and publish images only when application code changes, introduce better image retention and caching, and separate infrastructure lifecycle tasks from application deployment.

These improvements would make the pipeline more efficient without adding unnecessary complexity to a small project.
